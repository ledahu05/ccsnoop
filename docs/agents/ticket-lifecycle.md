# Ticket lifecycle: from idea to AFK implementation

How a ticket travels from a loose idea to merged code, and **which skill runs at each stage**. Two halves:

1. **Human-side (HITL)** — shaping work into `ready-for-agent` tickets, driven by a person invoking skills.
2. **AFK-side (Sandcastle)** — the headless loop in `.sandcastle/` that picks up those tickets and implements them.

The tracker is GitHub issues (`gh` CLI). See [issue-tracker.md](./issue-tracker.md) and [triage-labels.md](./triage-labels.md).

---

## Part 1 — Human-side: shaping the ticket

Skills here are all `disable-model-invocation: true` — a human invokes them with `/name`; the model never auto-fires them.

### Stage A — Decide the shape of the work

| Situation | Skill | Produces |
|---|---|---|
| Loose idea, too big for one session, route unclear | `/wayfinder` | A **map** issue (`wayfinder:map`) + child **decision tickets**; resolves them one at a time until the route is clear. Planning, not building. |
| Conversation already holds the design | `/to-spec` | A **spec** (PRD) issue, labelled `ready-for-agent`. No interview — pure synthesis. |
| A spec/plan/conversation to slice into work | `/to-tickets` | A set of **tracer-bullet** tickets (vertical slices), each declaring its blocking edges, labelled `ready-for-agent`. |

`/wayfinder` decision tickets themselves route to other skills per ticket type: `research` → `/research` subagent (AFK), `prototype` → `/prototype` (HITL), `grilling` → `/grilling` + `/domain-modeling` (HITL), `task` → manual unblock work.

### Stage B — Triage into a state

`/triage` moves an issue (or external PR, if the tracker treats PRs as a request surface) through a state machine:

```
unlabeled → needs-triage → { needs-info ⇄ needs-triage | ready-for-agent | ready-for-human | wontfix }
```

Every triage comment starts with `> *This was generated by AI during triage.*`. On the way it may:

- Check **redundancy** (already implemented → `wontfix`) and **prior rejection** (`.out-of-scope/*.md`).
- **Verify the claim** (reproduce a bug, confirm a PR's diff).
- **Grill** with `/grilling` + `/domain-modeling` if the request needs fleshing out.
- On `ready-for-agent`, post an **agent brief** — the durable spec the AFK agent reads.

**The handoff gate between the two halves is the `ready-for-agent` label + agent brief.** Everything above exists to produce a fully-specified, agent-grabbable ticket.

`/handoff` is orthogonal: it compacts a conversation into a doc (with a "suggested skills" section) so a fresh agent — human-run or otherwise — can continue. Not part of the automatic loop.

## Part 2 — AFK-side: the Sandcastle loop

`.sandcastle/main.ts` is a **RALPH-style** iterate-until-done loop (commits are prefixed `RALPH:`). Up to `MAX_ITERATIONS = 10` rounds; each round has three phases across four roles (planner, implementer, reviewer, merger). Each role is a headless agent driven by a `*-prompt.md` file — **the prompts inline the working method directly; they do not invoke the `/…` skills by name.**

Which model each role runs is not hardcoded: a **model profile** assigns a provider to each role, picked per run via `SANDCASTLE_PROFILE`.

| Profile | Planner | Implementer | Reviewer | Merger |
|---|---|---|---|---|
| `split` *(default)* | `glm-5.2[1m]` (z.ai) | `glm-5.2[1m]` (z.ai) | `claude-opus-5` (Anthropic) | `glm-5.2[1m]` (z.ai) |
| `opus` | `claude-opus-5` | `claude-opus-5` | `claude-opus-5` | `claude-opus-5` |

`npm run sandcastle` runs `split`, `npm run sandcastle:opus` runs `opus`; prefix either with `SANDCASTLE_DRYRUN=1` to print the wiring without launching an agent. `split` is the nominal regime — its reviewer runs a different model than the implementer, so it does not share the author model's blind spots. `opus` gives that guarantee up deliberately, for high-stakes tickets. See `docs/adr/0002-sandcastle-model-profiles.md`.

```
┌─ Iteration (×10 max) ───────────────────────────────────────┐
│                                                              │
│  Phase 1  Planner        plan-prompt.md    → <plan> JSON     │
│              │  picks parallelizable issues → {number,branch}│
│              ▼                                                │
│  Phase 2  per issue, ≤4 in parallel (own sandbox + branch):  │
│              Implementer #N   implement-prompt.md            │
│                 │ (only if it produced commits)              │
│                 ▼                                            │
│              Reviewer #N      review-prompt.md               │
│              ▼                                                │
│  Phase 3  Merger         merge-prompt.md   → merges branches │
│                                                              │
└──────────────────────────────────────────────────────────────┘
  loop exits early when the Planner returns zero issues
```

### Phase 1 — Planner  *(prompt not read — guardrail-blocked; behaviour below inferred from `main.ts`)*

An orchestrator agent analyses open issues and emits a `<plan>…</plan>` block of JSON: `{ number, title, branch }[]` — the parallelizable work for this round. Empty list → loop exits. **Which issues it selects (presumably the `ready-for-agent` ones) and whether it invokes any skill is defined in `plan-prompt.md`, which I could not read.**

### Phase 2a — Implementer (`implement-prompt.md`) — **this is where "TDD" lives**

Per issue, in a fresh Docker sandbox on its own branch (`npm ci` first). The prompt tells the agent to:

1. Pull the issue with `gh issue view --comments` (+ parent PRD if any). **Only** that issue.
2. Explore the repo, paying **extra attention to test files** touching the relevant code.
3. **"If applicable, use RGR"** — RED (write one test) → GREEN (implement to pass) → REPEAT → REFACTOR.
4. Feedback loop: `npm run typecheck` + `npm run test` before committing.
5. Commit with a `RALPH:` message (task done, PRD ref, decisions, files, blockers).
6. If incomplete, comment on the issue; **do not** close it (done later). Output `<promise>COMPLETE</promise>`.

### Phase 2b — Reviewer (`review-prompt.md`) — runs only if the Implementer committed

A single reviewer agent, on the same branch. It **mutates code** — writes tests, fixes what it can break, applies quality improvements, and commits (`RALPH: Review -`):

1. Read `git diff main..HEAD`; write tests to break anything dodgy — if it breaks, fix it.
2. Stress edge cases (empty/zero/negative, null/undefined, races, off-by-one, adjacent regressions).
3. Quality pass (reduce nesting, kill redundancy, clear names) — balanced against over-simplification.
4. Apply `.sandcastle/CODING_STANDARDS.md`; **preserve functionality** (change how, never what).
5. `typecheck` + `test` before and after. If already clean → do nothing. Output `<promise>COMPLETE</promise>`.

### Phase 3 — Merger  *(prompt not read — guardrail-blocked; behaviour below inferred from `main.ts`)*

One agent (`maxIterations: 10`) receives the list of branches-with-commits and their issues and merges them together. **Exact procedure and any skill use is in `merge-prompt.md`, which I could not read.**

## Does implementation use a TDD skill? — the precise answer

**TDD as a *technique*: yes, on both paths. The `/tdd` *skill*: only on the interactive path.**

| Path | TDD | Review |
|---|---|---|
| **AFK (Sandcastle)** | `implement-prompt.md` inlines RGR (red→green→refactor), conditional on *"If applicable"* — it does **not** invoke `/tdd`. | `review-prompt.md` inlines its own review method and **edits + commits**; it does **not** invoke `/code-review`. |
| **HITL (`/implement` skill)** | `/implement` says *"Use /tdd where possible, at pre-agreed seams"* — it **does** invoke the `/tdd` skill. | `/implement` then invokes `/code-review`. |

Two things worth keeping straight:

- **`review-prompt.md` ≠ the `/code-review` skill.** The AFK reviewer is one agent that writes tests, fixes, and commits. The `/code-review` skill is **report-only**, two-axis (Standards + Spec), run as parallel sub-agents, and changes nothing. Different tools with similar names.
- The `/tdd` skill and `.sandcastle/CODING_STANDARDS.md` agree on the substance — test at pre-agreed **seams**, behaviour not implementation, **vertical slices** (one test → one impl → repeat), never all-tests-first, never refactor while red.

## The whole pipeline at a glance

```
idea ─▶ /wayfinder ─┐
spec  ─▶ /to-spec ──┤
plan  ─▶ /to-tickets┘──▶ GitHub issue ──▶ /triage ──▶ [ready-for-agent + agent brief]
                                                              │
                                                              ▼
                                        Sandcastle loop: Plan → Implement → Review → Merge
                                        (RGR + CODING_STANDARDS.md inlined, not skills)
```

**Human skills shape the ticket; the AFK prompts re-express the same method (TDD, review, standards) inline.** The seam between the two halves is a single label: `ready-for-agent`.
